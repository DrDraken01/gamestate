# 0005 — Database schema: append-only predictions over a margin PMF

**Date:** 2026-09-28
**Status:** Accepted

## Context

The model now emits a margin distribution (ADR-0004), and the site will show
how a forecast moved through the week (product decision). The schema has to
store distributions, preserve prediction history, and keep the leakage
discipline that everything upstream depends on.

## Decisions

**Predictions are append-only, keyed by (run_id, game_id).** Never UPDATE. A
Tuesday forecast and a Saturday forecast for one game are two rows under two
runs. This is what makes forecast history a first-class feature instead of a
lossy overwrite, and it is why `model_runs` exists as the audit anchor: every
prediction points at a git_sha and a trained_through boundary, so "why did we
say 62% that week" is always answerable.

**Margin stored as a 121-element PMF, P(margin=k) for k in [-60,60].** Not
mu/sigma alone, which bakes in the Normal shape ADR-0004 proved wrong at key
numbers. Not raw simulation draws, which are heavy and force a scan per query.
The PMF on the integer lattice:
  - represents key numbers exactly (margins ARE integers);
  - answers every threshold as a suffix sum -- P(margin>3.5) = sum(pmf[65:]);
  - is identical whether filled by a discretised Normal today or simulation
    later. The representation survives the model change we know is coming.
  - ~1 KB/game.

mu and sigma are still stored alongside, as a convenient summary for thresholds
away from key numbers -- but the PMF is the source of truth.

**All instants are TIMESTAMPTZ.** kickoff_at is the row-level leakage boundary;
trained_through is the run-level one. Naive timestamps across timezones would
eventually let a late kickoff leak into an earlier prediction. This is not
theoretical -- it is the exact failure the whole feature layer is built to
prevent.

**market_lines is its own table with captured_at.** Lines move; opening vs
closing differs; movement is signal. One row per (game, book, capture)
preserves the trajectory that a single spread column would destroy.

**calibration stored by slice, not just overall.** ADR-0002 showed a change
that halved home-team bias barely moved aggregate log loss. Per-slice storage
is what makes subgroup bias visible, and it is the honest artifact the site is
built around.

## Migrations: plain SQL for now, Alembic later

Hand-numbered SQL files while the schema still changes weekly -- readable top to
bottom, no autogenerated churn. Adopt Alembic at the first schema change that
must preserve data in a live database; this file becomes migration 0001 there
with no rewrite.

## Validation

Applied against real PostgreSQL 16, not just eyeballed. Verified:
  - all five tables and indexes create cleanly;
  - both hot read paths work (latest-per-game via DISTINCT ON; thresholds via
    array suffix sums);
  - stored PMF sums to 1.0;
  - all four integrity constraints REJECT bad data (self-play, half-set scores,
    wrong PMF length, dangling FK).

`gamestate.db.pmf` mirrors the SQL indexing in Python, with a test
(`test_suffix_sum_matches_sql_indexing`) pinning the two together so they
cannot silently drift.

## Consequences

- The API read layer can stay thin: every threshold is one array operation.
- Storage grows ~1 KB per (run, game). A full season re-predicted daily for 18
  weeks is a few hundred MB -- comfortable.
- Push probabilities are storable but only trustworthy once simulation fills
  the PMF; until then the product must not surface them (ADR-0004).
